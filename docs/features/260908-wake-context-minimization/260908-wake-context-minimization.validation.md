# 260908-wake-context-minimization 用户验证要求

本次改动（framing v3 极简 + 静默唤醒 surface 压缩）已通过 171/171 单测（含真实 Session 端到端 surface 折叠断言、raced-turn 回归）。以下场景**无法用单测可靠覆盖**（涉及真实 agent-loop 的 inbox drain、真实模型行为与 GUI 渲染），需实机验证。

前置：重启 dsh 服务使 host 侧改动生效（lib 硬链接已同步到 web profile；重启会中断当前会话，注意安排）。

## 1. 静默唤醒后，模型上下文只剩墓碑（核心）

1. 在一个**长会话**（已有较多历史）里用面板或 `proactive_set` 设一个 `after_seconds: 300` 左右的闹钟，prompt 写明「没事就 no_reply」。
2. 等待触发，确认模型以 no_reply 静默结束（面板该闹钟的运行记录应显示决策 no_reply）。
3. 验证：后续普通回合中让模型复述「刚才那条 proactive 唤醒的完整报文内容」——模型应**无法复述**报文原文（最多记得有一条静默唤醒墓碑 `[dsh-proactive silent wake ...]`），证明压缩生效、上下文未被污染。
   - 预期残留 ≈ 70B/次；对比：改动前每次静默唤醒残留 ~2.6KB。

## 2. GUI transcript 完整性

1. 同上触发一次静默唤醒后，在 GUI 会话流中查看。
2. 预期：唤醒交换（notice 行 + 工具调用 no_reply）**仍然可见**，人类可读 transcript 不受 surface 压缩影响。

## 3. 可见回复的唤醒不被压缩

1. 设一个 prompt 为「到点后提醒我XXX，要发消息」的闹钟（预期模型写可见回复）。
2. 触发后模型发可见提醒。
3. 验证：下一回合模型仍记得自己发过该提醒（上下文未丢）；预算计数 +1 正常。

## 4. 唤醒期间用户发消息（raced turn）

1. 设一个短延迟闹钟（如 60s），在触发前后主动给会话发消息。
2. 预期：判策与预算只针对唤醒回合本身；若唤醒本身静默，则仍压缩、不误扣预算；若唤醒有可见回复，则回复保留在上下文中。

## 5. 重启后日志可加载（restore 兼容）

1. 触发过至少一次静默唤醒（日志中已有 tombstone/eraser 替换事件）后，重启 dsh。
2. 预期：会话正常加载，无 restore 校验报错；GUI transcript 仍完整。
